# ADR-0009：一致性备份、灾难恢复与本地数据保护

- 状态：已采纳（Phase 6，2026-11-13）
- 关联：ADR-0002（SQLite 持久化与 IPC）、ADR-0004（独立验收引擎）、ADR-0007（Claude Code Hooks）、ADR-0008（项目记忆与恢复）
- 迁移：`crates/xushu-core/migrations/0007_backup_restore_privacy.sql`
- 规范：`docs/architecture/DATA_PROTECTION.md`

## 1. 背景

Phase 6 要求把 XUSHU 从“功能可靠”提升到“数据生命周期可信”：

- 项目、任务、验收、验证证据、Claude 元数据、记忆、决策与恢复快照全部在本地 SQLite 中；
- 数据库使用 WAL，直接复制 `.db` 文件不能保证一致性；
- Hook Spool、伪名化 Salt、项目 `.claude` 配置、导出报告与 WebView 偏好是不同生命周期、不同敏感度的资产；
- 恢复是最高风险操作：不能把“备份文件存在”当成“可恢复”，也不能把“切换成功”当成“恢复通过验收”；
- 本地文件可能被替换为 Junction、符号链接或重解析点，Windows 路径安全不能只做字符串前缀判断；
- 用户需要能理解、能预检、能回退、能审计的备份与恢复流程。

## 2. 决策

### 2.1 使用 SQLite Online Backup API，而不是复制文件

备份通过 `rusqlite` 的 Online Backup API 从活动连接生成一致性快照。SQLite 只在应用数据目录内的私有工作区创建和校验快照：

1. 在隔离连接上整理为单文件（WAL 合并、`journal_mode=DELETE`）；
2. 执行 `PRAGMA integrity_check`、外键检查与业务关系检查；
3. 将单文件快照通过目录句柄复制到用户所选目标内的 `.partial-<uuid>/`，写入 `manifest.json`；
4. 通过该句柄回读清单，校验快照大小与 SHA-256；
5. 在目标目录内原子改名到 `xushu-backup-<UTC>-<short-id>/`；
6. 登记到 `backup_records`；登记失败则删除刚创建的自有备份目录。

不采用“复制 `.db`”或“只 checkpoint 后复制”，因为它们无法覆盖并发写、WAL 内容与写入中断。

### 2.1.1 用户选择的目录不直接交给 SQLite

SQLite 的 Unix VFS 在连接存续期按路径打开主库、WAL、SHM、journal 与临时文件。为防止不可信或可被替换的目标目录影响这些路径操作：

- SQLite 只在应用数据目录内的私有工作区创建、迁移和校验备份快照；用户选择的备份目标不传给 SQLite。
- 导出与恢复复制只使用已打开目录句柄：`openat` + `O_NOFOLLOW` + `O_EXCL` 创建目标文件，回读 SHA-256 后以 `NOREPLACE` 原子发布，并复核目录与文件身份。
- 恢复工作区、回退目录与清理操作同样绑定已校验的目录句柄与身份；不再按拼出的路径直接读写。
- macOS 额外拒绝可写 ACL、远程卷与关闭所有权的卷；所有祖先目录必须由当前用户或 root 拥有，且 group/other 无可写位（sticky 目录按系统语义处理）。
- 主库仍使用 WAL。既有 `-wal`、`-shm`、`-journal` 必须是当前用户拥有的单链接常规文件，符号链接在打开前被拒绝；SQLite 3.54.1 自身也对伴随文件使用 `O_NOFOLLOW`。

残余边界：具备同一 UID 且能修改应用数据目录的进程，或 root/管理员进程，仍可在连接存续期替换目录项；文件系统权限无法在同一用户域内形成隔离。该边界需要在威胁模型中明确，不能声称已被进程内路径检查完全消除。

### 2.2 备份范围是数据库快照，而不是整个 AppData

| 资产 | 是否进入备份 | 理由 |
|---|---|---|
| `xushu.db`（项目、任务、验收、验证、证据摘要、Claude 元数据、记忆、决策、恢复快照、备份登记、恢复审计） | 是 | 权威或不可重建的本地业务事实 |
| Hook Spool（`hook-inbox/pending`） | 否 | 瞬态待导入事件；恢复不应伪装成实时导入 |
| 伪名化 Salt（`hook-inbox`） | 否 | 运行时秘密；不导出、不显示；丢失只影响新旧伪名关联 |
| 项目 `.claude/settings.local.json` | 否 | 由项目自身持有；恢复不得自动重装 Hooks |
| `exports/` 验收报告 | 否 | 可从数据库重新生成；单独管理 |
| WebView2 本地存储（主题等） | 否 | 可重建的 UI 偏好，不是业务事实 |
| 日志 | 否 | 不持久化；stderr 仅运行时诊断 |

不打包整个 AppData，避免把 WebView 缓存、Hook 配置、Salt 或用户其他文件误纳入备份。

### 2.3 Manifest 格式 v1：只读 JSON + 单文件快照 + SHA-256

备份目录固定包含：

```text
xushu-backup-<UTC>-<short-id>/
├── manifest.json
└── xushu.db
```

Manifest 字段：格式版本、产品、备份 UUID、应用版本、来源 Schema、创建时间、来源（manual/automatic）、范围（database）、是否加密、是否完整、文件相对路径/大小/SHA-256。

约束：

- 只用 JSON，不执行任何备份内代码；
- 只允许一个相对路径 `xushu.db`；拒绝绝对路径、`..`、嵌套路径、重复文件；
- 清单大小 ≤ 256 KiB，数据文件 ≤ 2 GiB；
- 拒绝未知格式版本、未知字段、未来 Schema、未完成标记、加密标记；
- 允许旧 Schema（v1–当前）在隔离副本中升级；拒绝未来 Schema 降级；
- 校验和只证明“内容与清单一致”，不证明来源可信；UI 与文档明确说明。

### 2.4 恢复必须经过“只读预检 → 隔离验证 → 明确确认 → 受控切换 → 最终校验”

正式恢复不是一次文件复制，而是五个阶段：

1. **只读预检**：校验清单、SHA-256、Schema 兼容性、应用数据目录容量；显示当前/备份数据范围、备份之后当前数据库的时间戳变更计数、影响与警告。
2. **隔离恢复**：复制到应用数据目录自有的 `restore-workspaces/<token>/`，执行迁移、SQLite 完整性、外键、项目归属、验证/证据关系、记忆/决策修订与取代关系检查。
3. **明确确认**：一次性预检 token（15 分钟、最多 3 个、单次使用）+ 输入中文“恢复”+ 勾选风险确认；未确认不切换。
4. **受控切换**：先为当前数据库创建一致性回退副本；写恢复日志；合并 WAL、关闭连接；移动原数据库及 WAL/SHM 到回退目录；复制隔离副本到正式路径并校验 SHA-256；重新打开数据库。
5. **最终校验**：对切换后的正式数据库重新执行完整检查；通过后才记录 `completed`；失败则自动回退并记录 `rolled_back`/`rollback_failed`。

### 2.5 回退与恢复日志是恢复的一部分

- 切换前必须创建当前数据库的一致性回退副本；
- 原数据库、WAL、SHM 不删除，移动到 `restore-rollback/<operation>/`；
- `restore-journal.json` 记录阶段（prepared/switching/switched/completed）与路径；
- 正常完成后把日志归档为 `restore-journal-completed-*.json`；
- 应用启动时先检查日志：
  - `prepared`：切换尚未开始，原库不动，归档为 abandoned；
  - `switched` 或未完成的切换：自动回退到原数据库并验证；
  - 回退失败：明确显示 `needs_manual`，不删除任何回退文件；
- 启动恢复在数据库打开前执行，避免“先打开半切换数据库再补救”。

### 2.6 路径与文件系统安全

- 所有用户选择的目录必须是绝对路径；拒绝 UNC、设备路径、相对路径；
- 目录通过已打开句柄与 `FILE_ATTRIBUTE_REPARSE_POINT` 校验；任一祖先目录是 Junction/符号链接/重解析点即拒绝；
- 文件以不跟随重解析点的方式打开，校验普通文件属性并强制大小上限；
- 备份临时目录位于用户目标目录内，最终改名不假设跨卷原子性；恢复跨卷使用显式复制；
- 恢复只写入应用数据目录的正式数据库路径；备份读取只允许清单列出的单文件；
- 删除只作用于本应用登记、清单匹配、且目录中仅含已知文件的备份；手动备份不自动删除。

### 2.7 自动备份默认关闭，只在应用生命周期内运行

- 用户主动启用并配置目标、间隔与保留数量后才运行；
- 应用启动时与打开数据保护页时检查是否到期；应用关闭后不运行，不注册系统服务或后台常驻；
- 只对 `automatic` 来源执行保留清理；`manual` 备份永不自动删除；
- 自动备份失败只记录错误代码与时间，不删除旧备份。

### 2.8 Phase 6 不做备份加密

当前备份明确为未加密本地 SQLite 快照：

- 不实现“密码字段”式伪加密；
- 不硬编码密钥、不在日志/Manifest 中保存密钥；
- UI、文档与数据资产清单明确标注未加密，并提示只保存在受控位置；
- 若未来加密，必须新增 ADR，选择成熟加密库（如经审计的 AEAD）、定义密钥来源、丢失恢复与轮换流程，并保持旧备份可识别。不得自创密码算法。
- Windows DPAPI/CNG 可以把密钥绑定到当前用户/机器，但会显著增加“换机恢复”“账户损坏”“备份迁移”的复杂度；仅给备份文件加密码字段不是加密方案。Phase 6 评估后不实现，待完整密钥管理与恢复设计。

### 2.9 受限 IPC，不扩展现有权限面

新增命令只暴露领域操作：总览、创建/取消/校验/删除备份、策略读写、清理预览/执行、完整性检查、恢复预检/正式恢复、恢复提示关闭。前端仍无通用 SQL、Shell、任意文件系统写入或系统配置修改权限；路径、容量、状态与确认校验全部在 Rust 侧。

## 3. 后果

### 3.1 收益

- 备份是一致性快照，能够发现损坏、截断、清单不一致、未来 Schema 与路径穿越；
- 恢复前可以看见影响范围并完成隔离验证，不会直接覆盖当前数据库；
- 切换失败优先回退，进程崩溃后启动可自动恢复；
- Hook Spool、Salt 与项目配置不会被恢复流程误改；
- 数据资产、保留策略、敏感边界与未加密状态对用户可见。

### 3.2 代价

- 备份与恢复是阻塞式领域操作，执行期间其他数据库命令等待；
- 正式恢复有短暂数据库不可用窗口；无法做到零停机；
- 自动备份只在应用运行时发生，关闭后不保证按间隔执行；
- 备份不加密，用户需要自行保护备份文件；
- 恢复会替换整个数据库；备份之后产生的当前数据会丢失（回退副本保留）；
- 恢复不自动重装 Hooks，用户需要人工复核接入状态。

## 4. 被否决的方案

- **运行时复制 `.db`**：WAL 内容与并发写不一致，无法证明可恢复。
- **压缩整个 AppData**：会包含 Salt、Hook 配置、WebView 缓存与其他文件，范围与隐私不可控。
- **SQL dump**：不保留 SQLite 版本、索引、约束与 WAL 语义；恢复更易丢字段。
- **只保留最新备份**：无法回退到更早时点，也无法区分手动/自动。
- **直接覆盖当前数据库**：没有只读预检、隔离验证、回退与人工确认，风险不可接受。
- **在 UI 里只给备份文件加一个“加密”密码字段**：不构成真正加密，会造成虚假安全承诺。
- **自动重新安装/启用 Hooks**：恢复数据库不等于恢复项目配置文件，自动修改外部项目违反最小权限。
- **让前端持有通用路径/文件写入能力**：绕过 Rust 路径校验与恢复门禁。

## 5. 兼容、回滚与迁移

- 迁移 7 只新增 `backup_records`、`backup_settings`、`restore_operations`，不修改 1–6。
- 旧版本应用遇到 schema 7 会拒绝打开，避免静默降级；当前应用可读取 schema 6 备份并在隔离副本中升级到 7。
- 备份格式 v1 内的字段不接受未知扩展；需要新增字段时提升格式版本并提供明确的升级路径。
- 回滚应用版本不会删除备份、回退目录或恢复日志；但这些文件可能需要新版本才能解释，禁止静默删除。
- 若将来改变恢复算法，必须新增 ADR，并保留旧格式的识别与拒绝策略。

## 6. 验证

- Rust：`tests/backup.rs` 覆盖创建、清单、篡改、截断/损坏数据库、未来/旧 Schema、取消、并发写、自动清理、路径 Junction、预检、切换、回退、启动恢复、运行中验证阻断；`src/backup/*` 单元测试覆盖清单、路径与完整性规则。
- 前端：Vitest 覆盖数据保护页面、创建备份、校验、完整性检查、恢复向导的输入确认门禁、启动提示与显示辅助函数。
- 桌面：真实 Tauri/WebView2 隔离目录 E2E 覆盖备份 → 校验 → 修改 → 预检 → 损坏备份拒绝 → 正式恢复 → 最终校验 → 重启后一致；布局覆盖 500×480、1366×768、1600×900、1920×1080 与深浅主题。
- 正常用户数据库未被打开或写入；E2E 对 DB/WAL/SHM 三件套做前后指纹比较。
- 详细结果见 `docs/phases/PHASE_6_REPORT.md`。
